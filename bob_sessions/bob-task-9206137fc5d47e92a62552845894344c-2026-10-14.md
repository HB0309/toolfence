## Key decisions in the plan

### How `guard_on` / `datamark_on` reach the adapter

The runner already owns `DefenseConfig` (with `guard_on` and `datamark_on` booleans). The cleanest seam is **constructor injection**: the runner creates a fresh `NanobotAdapter(…, guard_on=defense.guard_on, datamark_on=defense.datamark_on)` per trial via an `adapter_factory` hook. The `defense` name string passed to `run_turn` is then used *only* for the `instructional` branch (write/delete workspace `AGENTS.md`). The adapter never needs to parse the name back into booleans.

### How the `tool-result` probe gets in as a Galaxium review row

`cancel-tool-result.json` describes a **passenger review** with the canary embedded — this is intentional. During a live run:

1. Before the turn, the adapter calls `POST /reviews` on Galaxium (the B-1a route) to seed a review row containing the canary for the relevant flight.
2. The agent runs the normal booking prompt; when it calls the reviews tool, it gets the seeded row back, placing the canary into the tool-result stream exactly as the probe intends.
3. After the turn, `DELETE /reviews/{id}` cleans up.

This is fully end-to-end — the canary flows through `GuardedProxy` in the real data path, not through a mock.
